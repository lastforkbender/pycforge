# Deterministic C Renderer — `c-renderer-v0.14.3`

`CRenderer` is total over validated `c-ir/0.14.3`. Invalid IR rejects before any
text or mapping set is returned. The renderer owns includes, whitespace,
indentation, braces, line breaking, declarators, precedence, parentheses,
literal escaping, LF endings, final newline, and the validated declaration
sequence. It never resolves Python/module names, sorts a dependency graph,
chooses rules, changes linkage, or infers ownership.

Rendering returns exact UTF-8 C plus provenance-derived many-to-many mappings.
Every source-derived mapping carries logical module ID, logical source name,
source-document/node references, RulePlan, C node, and exact byte/line/column
range. Separate source-symbol relationships connect imported alias spans to the
target binding/prototype/definition. No comment is fabricated for an import.

For Phase 12 the renderer accepts the reserved ASCII `pycm_` source-function
spellings already selected and validated by planning/C IR. It renders exactly
one translation unit in the supplied declaration order. It emits no module
header/include, section generated by discovery, module initializer, or second
output. Helper `pycf_` nodes retain isolated support-template provenance and the
existing renderer path.

The Phase 11 array/declarator/initializer/subscript grammar remains unchanged.
A one-document/no-import C IR renders byte-identically to Phase 11 for the same
source and configuration semantics. Reuse resets all output-local state.

An independent non-executing text parser validates the complete rendered
subset after rendering.

For Phase 13 the renderer emits every `CRecordDefinition` before helper/source
prototypes as one named `typedef struct` block. It preserves the supplied member
order, renders validated aggregate initializers with braces, places object-level
`const` on automatic record owners, and renders explicit member mode as `.` or
`->`. It does not infer a layout, reorder fields, synthesize padding directives,
select storage, call a constructor, or introduce a class runtime.

Scalar argument temporaries are already ordered C IR statements; the renderer
preserves that order before the aggregate declaration. Required `<stdint.h>`
and `<stdbool.h>` includes are still derived from the complete validated C IR,
including record member types. Class-free Phase 13 C IR renders the same bytes
as the matching Phase 12 translation unit.

For Phase 14A the renderer uses only the existing declaration, call,
conditional, and expression vocabulary. It emits each exact helper prototype
and definition once in validated registry order and preserves the supplied
left, right, result temporary sequence before any consuming statement. It does
not choose a helper, recognize a divisor literal, reconstruct a numeric proof,
fold an expression, or emit a runtime error path. Explicit historical Phase 13
C IR continues to render exact predecessor bytes.

For Phase 14B the renderer preserves the validated flat sibling guard order,
branch-local prerequisite statements, accumulator assignments, and fresh
identifier references already present in C IR. It renders only the existing
declaration, assignment, block, `if`, unary, binary, call, and identifier
grammar. It does not decide guard polarity, discover a region, hoist a
prerequisite, infer rolling-middle reuse, or choose a helper. The independent
text validator confirms balanced flat guarded structure and declaration-before-
use without consulting Python IR or conditional facts.

For Phase 14C the renderer receives only existing typed automatic declarations,
identifier references, and `CCallExpr` nodes. It preserves the supplied source-
order argument-temporary declarations and then renders the supplied pure
references in formal ordinal order. It does not inspect Python keyword names,
bind an actual to a formal, reorder prerequisite statements, infer a target,
emit named C arguments, or introduce runtime binding code. The independent text
validator continues to enforce declaration-before-use and the existing call
grammar without consulting keyword-call facts.

An explicit historical `c-renderer-v0.14` request remains total over validated
`c-ir/0.14` and produces exact Phase 14A bytes. The 0.14 renderer does not
acquire conditional-region behavior.
An explicit historical `c-renderer-v0.14.1` request remains total over
validated `c-ir/0.14.1`, preserves exact Phase 14B bytes, and does not acquire
keyword-call binding behavior.

For Phase 14D the renderer still receives only existing parameters, typed
automatic declarations, identifier references, and direct calls. It preserves
full validated C parameter order in prototypes and definitions, source-order
actual-temporary declarations, and supplied pure call references in full formal
order. It does not inspect `kwonlyargs`, encode a keyword-only marker in C,
classify a formal, bind a name, synthesize an omitted value, reorder
prerequisites, or emit runtime binding code.

The independent text validator continues to enforce prototype/definition
signature agreement, declaration-before-use, compatible call arity/types, pure
identifier-reference call arguments, and the existing direct-call grammar. The
exact source calling-mode proof, parameter kinds, binding, source/formal order,
and provenance remain fact/C IR obligations.

An explicit historical `c-renderer-v0.14.2` request remains total over validated
`c-ir/0.14.2`, produces exact Phase 14C bytes, and does not acquire
required-keyword-only declaration or call behavior. Under active
`c-renderer-v0.14.3`, a source selecting no Phase 14D behavior retains its
matching Phase 14C generated bytes.
